# Bit-exact reproduction of the legacy `ladybirdmnist` dataset

## Problem

The `ladybirdmnist` dataset (70,000 items, 10 morphs × 7,000) was generated
by a previous LPF revision whose CUDA path was *PyTorch eager* on
`cuda:0`. After migrating to the fused CUDA kernel introduced in commit
`ae9c88c`, re-running the saved model JSONs produces results that match
visually for ~99% of items but fail to reproduce the stored states bit
for bit. About 0.8% of items even diverge to a different attractor and
their morph/pattern PNGs disagree at the pixel level.

The dataset is the source of truth for downstream training, so the
fused kernel needs to match the legacy path bit-exactly while keeping
its performance.

## Investigation

### Step 1 — Algorithmic comparison

Diffed `lpf/models/twocomponentmodel.py`, `lpf/models/liawmodel.py`,
`lpf/solvers/eulersolver.py`, `lpf/solvers/solver.py` between the
pre-fused commit (`ae9c88c^`) and current `main`. The Python algorithm,
boundary handling, initializer, and parameter parsing are unchanged.

Diffed the new fused kernel (`lpf/kernels/csrc/include/stencil_core.cuh`,
`reactions.cuh`) against the old Python path: same Laplacian formula,
same reaction expression, same Euler update, same Neumann boundary
("dydt = 0 at edges"). No algorithmic difference.

→ The discrepancy must be a floating-point reordering effect.

### Step 2 — Bit-exact reference

Replayed the old algorithm directly in PyTorch eager mode on `cuda:0`,
element by element, on four representative items spanning the divergence
distribution (two ordinary items and two whose PNG pixels differ from
the stored data under the fused kernel):

| Item tag | PyTorch eager du | PyTorch eager dv |
|---|---:|---:|
| ordinary, tiny ~1e-5 | **0.000e+00** | **0.000e+00** |
| ordinary, mid ~2e-4  | **0.000e+00** | **0.000e+00** |
| PNG diff ~6e-1       | **0.000e+00** | **0.000e+00** |
| PNG diff ~2.2        | **0.000e+00** | **0.000e+00** |

→ Confirmed: **the dataset was generated by PyTorch eager on cuda:0**,
not by the cpu/NumPy path (which is close, ~3.8e-6 residual, but not
bit-exact). The eager path is the reference to match.

### Step 3 — Three hypotheses for the rounding difference

Three plausible sources of per-step ULP differences between the fused
kernel and the eager reference:

1. **`*dx2_inv` vs `/dx**2`** — The fused kernel pre-computes
   `dx2_inv = 1.0/dx**2 = 100.0f` (on host) and multiplies. The eager
   path was thought to divide. Hand-checked the constants:

   ```
   f32(0.1)               0x1.99999a0000000p-4
   f32(0.1)*f32(0.1)      0.010000001 0x1.47ae160000000p-7
   f32(0.01)              0.01        0x1.47ae140000000p-7
   1/dx2_a (f32)          99.99999    0x1.8ffffe0000000p+6
   1/dx2_b (f32)          100.0       0x1.9000000000000p+6
   1/(0.1**2)→f32         100.0       0x1.9000000000000p+6
   f32(100.0)             100.0       0x1.9000000000000p+6
   ```

   And empirically, `tensor / 0.01` and `tensor * 100.0f` produce
   identical results in PyTorch CUDA. **Hypothesis ruled out.**

2. **Caching `u^2*v/(1+k*u^2)` once vs computing it twice (for `f` and
   `g`)** — Independently of FMA, both forms produce the same float32
   value because the inputs are identical. **Hypothesis ruled out.**

3. **nvcc auto-FMA contraction (`--fmad=true`)** — `D*lap + f` and
   `c + dt*(D*lap + f)` live in the same function in the fused kernel,
   so by default nvcc fuses each pair into a single `fma` instruction,
   reducing rounding from 2 to 1. The eager path cannot do this — each
   ATen elementwise op is its own kernel — so its mul+add stays
   un-fused. **Hypothesis confirmed.**

### Step 4 — Verification

Rebuilt AOT fatbin with `--fmad=false` and re-ran the same four items:

| Item tag | du | dv | flag |
|---|---:|---:|---|
| ordinary, tiny ~1e-5 | **0.000e+00** | **0.000e+00** | BIT-EXACT |
| ordinary, mid ~2e-4  | **0.000e+00** | **0.000e+00** | BIT-EXACT |
| PNG diff ~6e-1       | **0.000e+00** | **0.000e+00** | BIT-EXACT |
| PNG diff ~2.2        | **0.000e+00** | **0.000e+00** | BIT-EXACT |

Re-ran the 669 worst-case items (every item with any morph/pattern
pixel difference under the original `--fmad=true --use_fast_math`
build):

| Metric | original (`--fmad=true`, fast_math on) | new (`--fmad=false`) |
|---|---:|---:|
| morph PNG bit-exact | 330 / 669 | **669 / 669** |
| pattern PNG bit-exact | 0 / 669 | **669 / 669** |
| `du_max` median | 1.11e-4 | **0** |
| `du_max` p90 | 1.65e-2 | **0** |
| `du_max` max | 3.79 | **0** |

A full-dataset revalidation with the new build matches bit-for-bit on
**every one of the 70,000 items**: `du_max = 0`, `dv_max = 0` for all
items, mismatches 0/70,000.

## Why this is essentially free

5-point stencils on 128×128 grids are firmly **memory-bound**. Per
pixel:

- 10 float32 loads (u, v × 5 neighbours) + 2 stores = **48 bytes**
- ~25 FLOPs (Laplacian + reaction + Euler update)
- **arithmetic intensity ≈ 0.5 FLOP/byte**

For a typical modern consumer GPU the compute roofline ridge point is
around 50 FLOP/byte — two orders of magnitude above where this kernel
operates. The kernel spends almost all of its time waiting on memory;
saving an ALU cycle with FMA does not move the wall-clock time.

### Single-batch benchmark (batch=128, 500k iters, 128×128, Liaw, fp32)

Each build was measured in a fresh Python subprocess (warm-up + 5 runs).
The fmad=false build was measured twice — first and last — to bound
clock/thermal drift between the two builds.

| Build | best (s) | median (s) | M item-iters/s (median) |
|---|---:|---:|---:|
| `--fmad=false` (run A) | 6.702 | **6.739** | **9.50** |
| `--fmad=true` | 6.753 | 6.788 | 9.43 |
| `--fmad=false` (run B) | 6.814 | **6.830** | **9.37** |

- `--fmad=true` vs `--fmad=false`: median +0.7% — within run-to-run drift.
- `--fmad=false` self-drift (run A → run B): +1.4% — *larger* than the
  fmad effect itself. The performance delta is therefore not measurable.

So the change buys bit-exact reproducibility for free.

## Changes applied

- [`lpf/kernels/aot/build.py`](../lpf/kernels/aot/build.py): add
  `--fmad=false` to both fatbin and `libsolver.so` nvcc commands;
  remove `--use_fast_math` (it gives no measurable speedup on
  reaction-diffusion kernels because there are no transcendentals,
  and it breaks IEEE-754 reproducibility).
- [`lpf/kernels/compiler.py`](../lpf/kernels/compiler.py): set the JIT
  NVRTC `_options` to `('--fmad=false',)`. The `fast_math` kwarg on
  `CuKernelManager`/solvers is intentionally kept as a no-op for
  backward compatibility.
- [`lpf/kernels/csrc/kernels.cu`](../lpf/kernels/csrc/kernels.cu): full
  header explaining why `--fmad=false` is required and what the perf
  cost is.
- [`lpf/kernels/csrc/solver_loop.cu`](../lpf/kernels/csrc/solver_loop.cu):
  short note pointing at `kernels.cu`.
- [`lpf/kernels/csrc/include/stencil_core.cuh`](../lpf/kernels/csrc/include/stencil_core.cuh):
  inline note in the doxygen header.

## Wider implications and policy

`--fmad` and `--use_fast_math` are the two most important rounding
controls in nvcc. Their correct setting is workload-dependent:

|                        | `--fmad`            | `--use_fast_math`                              |
| ---------------------- | ------------------- | ---------------------------------------------- |
| Memory-bound stencil   | **false** (free)    | **off**                                        |
| Compute-bound matmul   | true (~2× speedup)  | usually off (mixed precision is preferred)     |
| Transcendental-heavy   | true                | on (large speedup)                             |

Deep-learning libraries (cuBLAS, cuDNN, cuTLASS, FlashAttention, …) all
keep FMA on because their workloads are matmul-bound and the marketed
TFLOPS counts assume FMA. They generally keep `--use_fast_math` off and
trade precision via dtype (FP16/BF16/FP8) instead.

LPF is on the opposite end of that spectrum: a memory-bound 5-point
stencil with no transcendentals. Both flags are pure liabilities here
— they break reproducibility for no measurable speed gain — so the
correct default is `--fmad=false` and no fast_math, which is what LPF
now ships.
